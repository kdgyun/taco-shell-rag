# 구조와 동작

검색, 수집, 모델 실행과 답변 생성을 서로 다른 경계로 나눈다.
회사별 API나 업무 정책을 연결할 때는 해당 어댑터와 설정을 바꾸고 공통 게시 흐름은 그대로 둔다.

## 구성 요소

| 구성 | 맡는 일 | 직접 알지 않는 것 |
|---|---|---|
| `core/` | 문서·청크 규격, 색인 게시 순서와 검색 검증 | HTTP, Qdrant와 모델 라이브러리 |
| `adapters/sources.py` | 원본 전체 목록 수집 | 답변 생성과 모델 선택 |
| `adapters/inference.py` | 역할별 추론 HTTP 계약 | 가중치 로딩과 GPU 배정 |
| `adapters/catalog.py` | SQLite 게시 장부와 쓰기 잠금 | 검색 순위와 생성 모델 |
| `adapters/qdrant.py` | 벡터 저장·검색·버전 정리 | 원본 API와 최종 답변 |
| `gpu.py`, `model_config.py` | CUDA 모델 실행과 역할별 설정 | 업무별 정책과 사용자별 접근 권한 |
| `agent/` | 선택한 생성 모델의 읽기 도구 호출과 답변 | 색인 게시와 파일 수정 |
| `config.py`, `cli.py` | 설정 검증, 어댑터 조립과 명령 실행 | 회사별 기본 연결 정보 |

추론 역할은 `Embedder`와 `Reranker` 프로토콜로 분리한다.
다른 추론 API나 벡터 저장소를 쓰려면 해당 프로토콜의 어댑터를 구현하고 `config.py`에서 연결한다.
기본 구현이 모든 외부 API 규격을 자동 인식하는 것은 아니다.

## 색인 게시

```text
전체 목록 수집 → 문서 버전 비교 → 임베딩 → 벡터 저장
                                           ↓
체크포인트 저장 ← 이전 버전 정리 ← 게시 장부 전환
```

벡터 저장과 게시는 별개다. 새 벡터 쓰기가 끝난 문서만 장부의 게시 버전으로 전환하고
검색은 장부와 일치하는 청크만 반환한다. Qdrant에 남은 미게시·이전 버전 청크는 검색 결과에서 제외한다.
문서별로 게시하므로 소스 하나의 동기화가 전체 원자적 트랜잭션은 아니다.
중간에 실패하면 먼저 게시한 문서는 새 버전일 수 있지만 소스 체크포인트는 이전 값으로 남는다.
다음 동기화에서 같은 원본을 다시 비교하고 남은 작업을 이어간다.

수집 결과가 불완전하면 기존 목록에서 사라졌다는 이유로 문서를 삭제하지 않는다.
완전한 빈 목록은 실제 전체 삭제로 처리될 수 있으므로 인증 실패나 페이지 누락을 빈 성공 응답으로 바꾸면 안 된다.
벡터 쓰기 실패는 새 문서를 게시하지 않는다. 이전 버전 정리 실패는 `pending_cleanup`에 남겨 재시도한다.

SQLite 장부는 문서와 청크의 원문도 보관한다. Qdrant만 비공개로 두어서는 충분하지 않으며
`state` 볼륨에도 같은 수준의 접근 권한을 적용해야 한다.
다른 프로세스의 동기화와 겹치면 로컬 파일 잠금으로 쓰기를 거부한다.
여러 호스트가 서로 다른 장부로 같은 컬렉션에 쓰는 분산 색인 구조는 제공하지 않는다.

## 검색과 원문 조회

검색은 질의 임베딩, 후보 검색, 게시 버전 확인과 선택적 리랭킹 순서다.
임베딩에는 모델·리비전·차원과 인코딩 설정으로 만든 지문이 있다.
실행 응답의 지문이 사전 확인이나 기존 장부와 다르면 해당 벡터로 게시하거나 검색하지 않는다.
모델을 바꾸려면 새 컬렉션과 장부에서 다시 색인한다.

리랭커와 생성 모델은 벡터 공간을 바꾸지 않는다. 이 두 모델만 교체할 때는 재색인할 필요가 없다.
리랭킹을 켰는데 서비스가 중단되면 검색은 오류를 반환한다. 조용히 cosine 순위로 전환하지 않는다.
색인은 리랭커를 호출하지 않으므로 리랭커 중단만으로 막히지 않는다.

`search`는 제한된 후보와 청크를 반환한다. 전체 문서나 전체 소스를 읽었다는 뜻은 아니다.
`get_document`에는 검색 결과의 정확한 문서 키와 버전을 지정한다.
다음 청크가 있으면 `next_start`로 이어서 읽으며 색인이 갱신되어 버전이 사라지면 다시 검색한다.
검색 결과가 비거나 읽기에 실패해도 정책이 없다고 단정하지 않는다.

## 생성 모델과 agent

검색 MCP에는 생성 모델이 필요 없다. 연결한 클라이언트가 근거를 읽고 답변한다.
선택적 HTTP agent는 Claude API나 OpenAI 호환 API에 같은 읽기 도구를 넘긴다.
Claude CLI 어댑터는 설치된 CLI가 자신의 실행 루프를 관리하며 HTTP agent와 실행 정보의 범위가 다르다.

HTTP agent에서 실행할 수 있는 도구는 `search`, `get_document`, `status`다.
단계·호출·근거 크기 한도를 넘으면 완료 답변 없이 `budget_exhausted`를 반환한다.
`required_tools`를 설정하면 지정한 읽기가 빠진 초안도 완료 답변으로 내보내지 않는다.
도구 호출이 없는 모델은 사용자가 `rag` 모드를 명시해 검색 후 한 번 생성하도록 연결한다.
어느 모드도 답변의 정확성이나 인용의 의미를 자동 보증하지 않는다.

## 인증과 신뢰 범위

HTTP MCP는 Bearer 토큰과 Host·Origin 검사를 사용한다. 기본 노출 주소는 호스트의 loopback이다.
추론 API와 Qdrant는 Compose 내부망에 두며 외부 포트를 열지 않는다.
MCP의 읽기 전용 도구는 원본에 쓰지 않지만 허용된 접속자는 해당 배포의 모든 소스를 읽는다.
문서별 ACL이나 여러 사용자의 권한 분리는 구현하지 않았으므로 데이터 권한별로 인스턴스를 나눈다.

문서 본문과 도구 응답은 근거 자료로 다루고 실행 지시로 받아들이지 않는다.
이 규칙은 prompt injection 방어의 일부이며 완전한 격리를 보증하지 않는다.
원본 API와 생성 API의 자격 증명은 서로 다른 `token_env`로 지정한다.
설정에는 비밀값 자체 대신 환경변수 이름을 적는다. 기본 Compose는 같은 `.env`를 애플리케이션에
전달하므로 프로세스별 자격 증명 격리가 필요하면 서비스의 환경변수 전달 범위도 별도로 좁힌다.
