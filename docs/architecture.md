# 구조와 동작

문서를 수집해 검색에 반영하는 일은 Python indexer가 맡습니다. Go MCP 서버는 그 문서를 검색하고,
답변은 검색 결과를 받은 클라이언트나 에이전트가 작성합니다. 임베딩과 리랭킹은 별도의 GPU 추론 API를 호출합니다.

데이터를 추가할 때는 수집기를, 모델을 바꿀 때는 추론 설정이나 어댑터를 수정합니다.
특정 회사의 API나 업무 정책을 연결하더라도 문서 저장과 검색 코드를 함께 고치지 않도록 나눈 구조입니다.

## 코드에서 찾아볼 위치

| 하려는 작업 | 위치 | 이곳에서 처리하는 일 |
|---|---|---|
| MCP 서버 실행 방식 변경 | Go `cmd/mcp-http/`, `cmd/mcp-stdio/` | HTTP·stdio 서버 시작 |
| 도구 입력·응답, HTTP 인증 변경 | Go `internal/mcp/`, `internal/transport/http/` | 도구 등록, Bearer 인증과 요청 처리 |
| 검색 방식 변경 | Go `internal/retriever/` | 벡터·키워드 검색, 순위 결합, 반환할 문서 버전 확인 |
| 검색에 쓰는 외부 서비스 교체 | Go `internal/catalog/`, `internal/vectorstore/`, `internal/inference/` | SQLite·벡터 저장소·추론 API 조회 |
| 데이터 수집이나 색인 변경 | Python `indexer/` | 원문 수집, 청크 분할, 벡터 저장, 문서 버전과 BM25 갱신 |
| GPU 모델 실행 방식 변경 | Python `embedder/`, `reranker/` | 역할별 CUDA 모델 로딩과 추론 |
| 추론 API와 모델 설정 변경 | Python `gpu.py`, `model_config.py` | HTTP 앱 구성, 임베딩·리랭커 설정 적용 |
| 답변 생성 방식 변경 | Python `agent/` | Go MCP 도구 호출, 생성 모델 연결 |

Python 경로는 `src/taco_shell_rag/` 아래에 있습니다. 공통 자료형과 인터페이스는 Go의 `internal/core/`,
Python의 `core/`에 두고, 실제 연결은 Go의 `internal/app/`과 Python의 `config.py`에서 정합니다.
`gpu.py`는 HTTP 앱과 프로세스를 구성하며 모델을 실행하는 코드는 각 역할의 폴더에 있습니다.

임베딩과 리랭커는 `Embedder`, `Reranker` 인터페이스로 따로 연결합니다.
외부 API를 교체할 때는 그 API에 맞는 어댑터가 필요합니다. 특히 벡터 저장소와 추론 API는
Python의 저장 방식과 Go의 조회 방식이 맞아야 하므로 양쪽을 함께 확인합니다.

## 새 문서가 검색에 반영되는 과정

벡터를 저장했다고 바로 검색 결과로 내보내지는 않습니다. SQLite 문서 DB에는 원문과 청크뿐 아니라
현재 검색에 사용할 문서 버전을 기록합니다. 벡터 저장을 마치면 검색 대상 버전을 새 버전으로 바꿉니다.

```text
전체 목록 수집 → 문서 버전 비교 → 임베딩 → 벡터 저장
                                           ↓
체크포인트 저장 ← 이전 버전 정리 ← 검색 대상 버전 변경
```

indexer는 새 벡터를 모두 저장한 문서부터 검색에 반영합니다. 검색에 사용할 버전 정보와 BM25 색인은 같은 SQLite
트랜잭션에서 바꿉니다. Go 서버는 Qdrant에서 찾은 청크를 이 기록과 대조하므로 검색에 반영하기 전의 벡터나
이전 버전의 벡터가 Qdrant에 남아 있어도 검색 결과에 섞이지 않습니다.

검색에 사용할 버전은 문서별로 바꿉니다. 소스 하나를 동기화하는 동안 모든 문서가 한꺼번에 전환되는 방식은 아닙니다.
중간에 실패하면 먼저 처리한 문서는 새 버전이고 나머지는 이전 버전일 수 있습니다. 소스의 체크포인트는
버전 갱신과 이전 데이터 정리가 끝나야 바뀌므로, 다음 동기화에서 원본을 다시 비교해 남은 작업을 이어갑니다.

### 중간에 실패했을 때

| 실패한 작업 | 처리 |
|---|---|
| 원본 목록을 끝까지 수집하지 못함 | 목록에서 빠졌다는 이유로 기존 문서를 삭제하지 않습니다. |
| 새 벡터 저장 | 해당 문서의 새 버전을 검색에 반영하지 않습니다. |
| 이전 버전 정리 | `pending_cleanup`에 남겨 다음에 다시 시도합니다. |

완전한 빈 목록은 원본 문서가 모두 삭제됐다는 뜻으로 처리될 수 있습니다. 인증 실패나 페이지 누락을
빈 성공 응답으로 바꾸면 기존 자료를 지울 수 있으므로, 수집기는 실패와 빈 목록을 구분해야 합니다.

같은 문서 DB에 여러 동기화 프로세스가 동시에 쓰려고 하면 로컬 파일 잠금을 얻지 못한 쪽을 거부합니다.
여러 호스트가 각자의 문서 DB로 같은 컬렉션에 쓰는 분산 색인은 지원하지 않습니다.
SQLite 문서 DB에도 원문이 저장되므로 `state` 볼륨의 접근 권한은 Qdrant와 같은 수준으로 관리합니다.

## 검색부터 원문 조회까지

기본 검색 도구인 `search`는 질문을 한 번 임베딩해 찾은 벡터 후보와 BM25 키워드 후보를 RRF로 합칩니다.
리랭킹을 켜 두었다면 GPU 리랭커가 이 후보를 다시 정렬합니다. 키워드 검색은 모델 없이 실행하고,
계획형 검색은 질문에 있는 식별자·인용문과 출처별 검색을 더합니다. 도구별 입력과 한도는
[검색 가이드](retrieval.md)에 정리했습니다.

검색 결과만으로 문서 전체를 읽은 것은 아닙니다. 앞뒤 내용을 확인하려면 결과의 문서 키와 버전을
`get_document`에 넘깁니다. 남은 청크는 `next_start`로 이어서 읽습니다. 그사이 색인이 갱신되어
해당 버전을 조회할 수 없으면 다시 검색해 현재 버전을 받습니다. 검색이 비거나 조회가 실패했다는 이유로
원문에도 해당 정책이 없다고 판단해서는 안 됩니다.

### 모델을 바꿨을 때

색인할 때와 검색할 때 같은 임베딩 설정을 쓰는지 확인하기 위해 모델·리비전·차원·인코딩 설정으로 지문을 만듭니다.
실제 추론 응답의 지문이 사전 확인 결과나 문서 DB에 기록된 값과 다르면 해당 요청을 실패로 처리합니다. Go 서버는 지문 문자열뿐 아니라
문서 DB의 모델·리비전·인코딩 정보도 비교하므로 문자열만 같게 돌려주는 잘못된 응답도 거부합니다.
임베딩 모델을 교체할 때는 새 컬렉션과 SQLite 파일에 다시 색인합니다.

리랭커와 생성 모델은 저장된 벡터를 바꾸지 않으므로 두 모델만 교체할 때는 재색인이 필요 없습니다.
다만 리랭킹을 사용하도록 설정한 상태에서 리랭커가 중단되면 검색은 오류를 반환합니다.
cosine 순위로 대신 응답하지는 않습니다. 색인은 리랭커를 호출하지 않아 이 중단만으로 막히지 않습니다.

## 답변을 만드는 방법

검색 MCP만 쓸 때는 연결한 클라이언트가 근거를 읽고 답변합니다. 생성 모델이 필요한 부분은 별도의 에이전트입니다.
HTTP 에이전트는 Claude API나 OpenAI 호환 API를 호출하고, Claude CLI 어댑터는 설치된 CLI에 실행을 맡깁니다.
CLI가 내부 과정을 관리하므로 두 방식에서 확인할 수 있는 실행 정보에는 차이가 있습니다.

두 방식 모두 Go MCP의 다섯 읽기 도구만 허용합니다. 단계·호출 횟수·근거 크기 한도를 넘으면
완료 답변 대신 `budget_exhausted`를 반환합니다. `required_tools`를 지정했다면 필요한 읽기가 빠진 초안도
완료 답변으로 내보내지 않습니다. 도구 호출을 지원하지 않는 모델은 사용자가 `rag` 모드를 지정해
검색 후 한 번 생성하도록 연결합니다. 이런 확인은 실행 절차를 검사하는 것이며 답변의 정확성이나 인용의 의미까지 판단하지는 않습니다.

## 접속과 데이터 접근 권한

HTTP MCP는 Bearer 토큰과 Host·Origin 검사로 접속을 제한하며, 기본 주소는 호스트의 loopback입니다.
추론 API와 Qdrant는 Compose 내부망에서만 연결합니다. MCP 도구는 원본을 수정하지 않지만,
접속한 사용자는 그 배포에 연결된 모든 소스를 읽을 수 있습니다. 문서별 ACL이나 사용자별 권한 분리는
구현되어 있지 않으므로 접근 권한이 다른 자료는 인스턴스를 나눠 운영합니다.

문서 본문과 도구 응답에 적힌 지시는 실행 명령이 아니라 참고 자료로 취급합니다. 이는 prompt injection에
대응하는 규칙 중 하나이며, 이 규칙만으로 완전한 격리가 이뤄지는 것은 아닙니다.

원본 API와 생성 API의 인증 정보는 각각 다른 `token_env`로 지정합니다. 설정 파일에는 실제 토큰 대신
환경변수 이름을 적습니다. 기본 Compose는 같은 `.env`의 값을 애플리케이션에 전달하므로
프로세스마다 다른 인증 정보만 받게 하려면 서비스별 환경변수 전달 범위도 따로 설정해야 합니다.
