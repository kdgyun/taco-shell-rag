# 검색

질문으로 문서를 찾을 때는 `search`, 번호나 경로처럼 정확한 단어를 찾을 때는 `keyword_search`를 사용합니다.
여러 출처를 함께 확인해야 하면 `deep_search`로 탐색하고, 결과의 앞뒤 문맥은 `get_document`로 읽습니다.
이 도구들은 Go MCP 서버에서 실행하며 Python indexer가 저장한 자료를 조회합니다.
답변은 검색 결과를 받은 클라이언트나 별도로 연결한 에이전트가 작성합니다.

## 도구 고르기

| 하려는 일 | 도구 | 동작 |
|---|---|---|
| 질문과 관련된 근거 찾기 | `search` | 벡터·BM25 검색을 합치고 필요하면 GPU로 리랭킹합니다. |
| 티켓 번호·버전·경로 찾기 | `keyword_search` | BM25로 검색 대상 문서를 찾습니다. 모델을 호출하지 않습니다. |
| 여러 자료와 식별자를 함께 확인 | `deep_search` | 하이브리드 검색에 식별자·인용문·출처별 검색을 더합니다. |
| 검색 결과 앞뒤 읽기 | `get_document` | 문서 키와 버전에 해당하는 청크를 구간별로 조회합니다. |
| 동기화 상태 확인 | `status` | 소스별 체크포인트, 마지막 시도와 성공, 오류 종류, 정리 대기 수를 읽습니다. |

검색 도구에는 `query`와 `limit`을 넘깁니다. `limit`은 기본 5, 최대 20입니다.
특정 소스만 찾으려면 설정에 등록한 연결 ID를 `source_id`로 지정합니다.
각 결과에는 원래 문서와 청크의 출처·버전이 함께 담깁니다.

```sh
uv run taco search '환불 정책'
uv run taco search 'ABC-123' --mode keyword
uv run taco search 'ABC-123의 환불 정책과 구현 경로' --mode planned
uv run taco search 'refund policy' --mode dense
```

CLI 검색도 Go stdio MCP를 호출합니다. 소스에서 설치했다면 먼저 `make build`를 실행합니다.
컨테이너의 indexer 이미지에는 필요한 stdio 바이너리가 들어 있습니다.

## 기본 검색의 후보와 순위

하이브리드 검색은 다음 순서로 후보를 고릅니다.

1. 질문을 GPU에서 한 번 임베딩하고 Qdrant에서 벡터 후보를 찾습니다.
2. SQLite FTS5에서 본문·제목·경로의 BM25 후보를 찾습니다.
3. 두 순위를 RRF로 합치고 같은 문서 버전의 같은 청크를 중복 제거합니다.
4. 리랭킹을 켰다면 GPU 리랭커가 합친 후보를 다시 정렬합니다. 껐다면 RRF 순서를 반환합니다.

cosine과 BM25는 서로 점수 척도가 달라 원점수를 직접 더하지 않습니다.
응답의 `score_kind`를 보면 어떤 점수인지 알 수 있습니다.

| 값 | 의미 |
|---|---|
| `cosine` | 벡터 유사도 |
| `bm25` | 키워드 검색 점수 |
| `rrf` | 여러 검색 순위를 결합한 점수 |
| `reranker_raw_uncalibrated` | 리랭커가 반환한 보정 전 점수 |

검색 결과의 점수는 정확도나 확률이 아닙니다. 후보가 어느 검색에서 나왔는지는 `matched_by`에 기록합니다.
벡터 검색만 쓰려면 `mode=dense`를 직접 지정합니다. 하이브리드 검색 도중 서비스가 실패했다고
벡터 검색으로 바꾸거나 리랭킹을 생략해 성공으로 응답하지는 않습니다.

## 번호와 단어를 찾을 때

`keyword_search`는 임베딩과 리랭커를 호출하지 않으므로 모델 서비스가 중단되어도 사용할 수 있습니다.
키워드 순위 계산은 일반 서버 작업이며, GPU 추론을 CPU로 대신하는 기능은 아닙니다.

검색은 대소문자를 구분하지 않는 토큰 기준입니다. 기본 `match=all`은 모든 검색 토큰을,
`match=any`는 하나 이상의 토큰을 요구합니다. SQL·FTS 연산자, 정규식, 임의의 부분 문자열 검색은 지원하지 않습니다.
질의는 최대 24토큰입니다. `match=all`에서 넘치면 조건을 잘라 실행하는 대신 질의를 좁히라는 오류를 반환합니다.

FTS가 문장부호를 나눈 뒤에도 원문 식별자를 대조합니다. `ABC-123`과 `ABC-1234`,
`2.17`과 `2.17.0`을 같은 식별자로 취급하지 않습니다.
한글은 공백으로 나누므로 `환불`과 `환불정책`도 다른 토큰입니다.
키워드 검색은 형태소 분석이나 오탈자 교정을 하지 않습니다. 단어 형태가 다를 수 있는 질문은 하이브리드 검색도 함께 시도합니다.

## 여러 자료를 함께 찾을 때

`deep_search`는 질문에서 티켓 형식의 ID, 버전, 경로, 코드 식별자, 따옴표로 감싼 구절을 추출합니다.
이를 키워드로 검색하고 설정된 출처마다 벡터 검색도 수행한 뒤 전역 하이브리드 검색 결과와 함께 고릅니다.
벡터 검색에는 처음 만든 질문 임베딩을 재사용합니다. 검색 계획은 규칙으로 만들며
서버 LLM이 질문에 없던 조건이나 사실을 만들어 검색하지 않습니다.

어디까지 찾았는지는 다음 필드로 확인합니다.

| 필드 | 확인할 내용 |
|---|---|
| `plan` | 실제로 탐색한 식별자·출처와 한도 때문에 생략한 수 |
| `anchor_coverage` | 각 식별자가 최종 반환한 근거에 포함되어 있는지 여부 |
| `coverage_gaps` | 확인하지 못한 식별자, 후보 한도, 읽지 못한 범위 |

후보에 있었더라도 응답 한도 때문에 내보내지 못한 근거는 확인된 것으로 표시하지 않습니다.
결과가 한 출처나 문서에만 몰리지 않게 고르지만 관련 자료 전체를 읽었다는 뜻은 아닙니다.
클라이언트는 이 정보를 보고 추가 검색이나 원문 조회를 결정합니다.

## 검색량 조절

`taco.toml`의 `[retrieval]`에서 설정합니다. 모델이나 데이터 소스 선택과 별도로 바꿀 수 있습니다.

```toml
[retrieval]
mode = "hybrid"
candidate_limit = 160
rrf_k = 60
dense_weight = 1.0
keyword_weight = 1.0
max_plan_terms = 6
max_plan_sources = 4
max_evidence_chars = 16000
```

| 설정 | 제한하는 작업 |
|---|---|
| `candidate_limit` | 리랭커에 넘길 후보 수입니다. 요청 크기에 따라 늘리되 최대 160개를 넘기지 않습니다. |
| `max_plan_terms` | 계획형 검색에서 추가로 탐색할 식별자 수입니다. |
| `max_plan_sources` | 계획형 검색에서 추가로 탐색할 출처 수입니다. |
| `max_evidence_chars` | 반환할 근거의 크기입니다. 넘치는 청크는 자르지 않고 생략 수에 기록합니다. |

식별자·출처 탐색을 한도로 생략한 수는 응답에 표시합니다.
검색과 원문 구간 조회 모두 문서 전체나 색인 전체를 빠짐없이 확인하는 기능은 아닙니다.

## 서비스가 준비됐는지 확인

| 확인 방법 | 알 수 있는 것 | 확인하지 않는 것 |
|---|---|---|
| HTTP MCP의 `/healthz` | 전송 계층이 응답하는지 | 모델 로딩, Qdrant 접속, 색인 완료 |
| MCP의 `status` | 문서 DB와 동기화 기록 | 추론 API 동작 |
| `keyword_search` | 키워드 검색 동작 | 임베딩·리랭커 준비 여부 |
| `search`, `deep_search` | 실제 사용할 검색 경로의 동작 | 자료 전체의 완전성 |

상태 점검 후에는 사용하려는 `search`나 `deep_search`를 직접 호출해 봅니다.

## 색인 갱신 중의 검색

문서와 벡터를 쓰는 쪽은 Python indexer입니다. Go 서버는 SQLite를 읽기 전용으로 열고 조회만 합니다.
indexer가 벡터 저장을 마치면 문서 버전과 BM25 색인을 같은 트랜잭션에서 바꿉니다.
Go는 Qdrant 후보의 버전이 문서 DB의 검색 대상 버전과 같은지 확인하고 리랭킹 뒤에도 다시 확인합니다.
그래서 이전 벡터 정리가 늦어져도 현재 검색 대상과 다른 버전의 청크를 근거로 내보내지 않습니다.

문서 DB에 FTS5 색인이 없으면 다음 `sync`가 검색 대상 문서를 읽어 키워드 색인을 준비합니다.
임베딩 설정이 같다면 벡터를 다시 만들 필요는 없습니다. Python SQLite에 FTS5 지원이 필요하며
기본 컨테이너 이미지에는 포함되어 있습니다. 테스트에서도 Python과 Go의 실제 SQLite로 확인합니다.

SQLite 문서 DB는 WAL을 사용합니다. Go의 SQL 연결이 읽기 전용이어도 공유 메모리 파일에 접근해야 하므로
기본 Compose는 두 서비스에 같은 `state` 볼륨을 연결합니다. `immutable=1`로 열면 새 WAL 내용을
놓칠 수 있어 사용하지 않습니다. 상태 볼륨을 다른 호스트에 복제해 따로 조회하는 분산 구성은 지원하지 않습니다.
