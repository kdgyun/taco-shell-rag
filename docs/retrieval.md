# 검색

검색과 MCP는 Go에서 실행한다. Python indexer가 게시한 문서와 GPU 추론 API를 사용하며
서버 안에서 답변을 생성하지 않는다. 생성 모델은 검색 결과를 읽는 클라이언트나 선택적 agent에 연결한다.

## 도구 선택

| 도구 | 사용할 때 | 실행 범위 |
|---|---|---|
| `search` | 질문과 관련된 근거를 찾을 때 | 벡터·BM25 결합, 선택적 GPU 리랭킹 |
| `keyword_search` | 티켓 번호, 버전, 경로와 정확한 단어를 찾을 때 | 게시 문서의 BM25 검색, 모델 호출 없음 |
| `deep_search` | 여러 자료를 비교하거나 특정 식별자를 함께 확인할 때 | 하이브리드 검색, 질문의 식별자·인용문 검색, 출처별 탐색 |
| `get_document` | 검색 청크 앞뒤의 문맥을 읽을 때 | 정확한 문서 키·버전의 청크 구간 |
| `status` | 색인 시도와 마지막 성공을 확인할 때 | 소스 체크포인트, 오류 종류와 정리 대기 수 |

모든 검색은 `query`, `limit`, 선택적 `source_id`를 받는다. `limit`은 기본 5, 최대 20이다.
`source_id`는 설정한 연결 ID여야 한다. 문서·청크의 출처와 버전은 결과마다 그대로 반환한다.

```sh
uv run taco search '환불 정책'
uv run taco search 'ABC-123' --mode keyword
uv run taco search 'ABC-123의 환불 정책과 구현 경로' --mode planned
uv run taco search 'refund policy' --mode dense
```

이 명령도 별도의 Python 검색 서버를 만들지 않고 Go stdio MCP에 연결한다.
소스 설치는 먼저 `make build`로 바이너리를 준비한다. 컨테이너의 indexer 이미지에는 stdio 바이너리가 포함된다.

## 하이브리드 검색

질의를 GPU에서 한 번 임베딩해 Qdrant의 벡터 후보를 찾는다. 별도로 SQLite FTS5에서
본문·제목·경로의 BM25 후보를 구한다. 두 순위를 RRF로 결합하고 같은 문서 버전·청크는 중복 제거한다.
서로 척도가 다른 cosine·BM25 점수를 직접 더하지 않는다.

리랭킹을 켜면 결합한 후보를 설정한 GPU reranker에 넘긴다. 꺼 두면 RRF 순위를 반환한다.
`mode=dense`는 BM25를 사용하지 않는 명시적 선택이다. 하이브리드 검색 중 일부 서비스가 실패했을 때
성공한 것처럼 벡터 검색으로 바꾸거나 리랭킹을 생략하지 않는다.

응답의 `score_kind`는 `cosine`, `bm25`, `rrf` 또는 `reranker_raw_uncalibrated`다.
이 값은 점수의 종류이며 정확도나 확률이 아니다. `matched_by`에는 후보를 찾은 검색 경로가 남는다.

## 키워드 검색

`keyword_search`는 임베딩·리랭킹 서비스를 호출하지 않아 모델이 중단돼도 사용할 수 있다.
모델 추론을 CPU로 대체하는 기능은 아니다. 키워드 순위 계산은 일반 서버 작업이다.

대소문자를 구분하지 않는 토큰 검색이며 기본 `match=all`은 모든 검색 토큰, `match=any`는
하나 이상을 요구한다. SQL·FTS 연산자, 정규식이나 임의의 부분 문자열 검색은 지원하지 않는다.
키워드 질의는 최대 24토큰이다. `match=all`에서 이 한도를 넘으면 일부 조건을 생략하지 않고 질의를 좁히도록 오류를 반환한다.
FTS가 문장부호를 분리한 뒤에도 원문에서 식별자를 확인한다. 예를 들어 `ABC-123`은 `ABC-1234`,
`2.17`은 `2.17.0`과 같은 식별자로 취급하지 않는다.

한글은 공백으로 구분된 토큰 기준이다. `환불`과 `환불정책`을 자동으로 같은 단어로 해석하지 않으며
형태소 분석이나 오탈자 교정도 하지 않는다. 이런 질문에는 하이브리드 검색을 함께 사용한다.

## 계획형 검색

`deep_search`는 원문 질문에서 티켓 형식의 ID, 버전, 경로, 코드 식별자와 따옴표로 감싼 구절을 추출한다.
전역 하이브리드 검색에 이 식별자의 키워드 검색과 설정된 출처별 벡터 검색을 더한다.
모든 벡터 탐색은 처음 만든 질의 임베딩을 재사용한다.

계획은 규칙 기반이다. 서버 LLM이 새 사실을 가정하거나 질문에 없는 조건을 만들어 검색하지 않는다.
`plan`에는 실제 탐색한 식별자와 출처, 한도로 생략한 수가 담긴다.
`anchor_coverage`는 각 식별자가 최종 반환 근거에 포함되는지 표시한다. 후보에는 있었어도
응답 한도 때문에 반환하지 못했다면 확인된 근거로 표시하지 않는다.

출처와 문서가 한쪽으로 몰리지 않도록 결과를 고르되 이를 관련 자료 전체를 읽었다는 보증으로 해석하지 않는다.
확인되지 않은 식별자, 후보 한도와 읽지 못한 범위는 `coverage_gaps`로 남긴다.
클라이언트가 후속 질문이나 원문 조회를 결정한다.

## 설정

`taco.toml`의 `[retrieval]`에서 조절한다. 모델 선택이나 소스 연결과 독립적이다.

```toml
[retrieval]
mode = "hybrid"
candidate_limit = 160
rrf_k = 60
dense_weight = 1.0
keyword_weight = 1.0
max_plan_terms = 6
max_plan_sources = 4
max_evidence_chars = 16000
```

후보는 요청 크기에 따라 늘리되 `candidate_limit`을 넘겨 리랭킹하지 않는다. 최대 160개다.
`max_plan_terms`와 `max_plan_sources`는 추가 탐색의 상한이다. 생략한 개수는 응답에 표시한다.
`max_evidence_chars`를 넘는 청크는 원문을 잘라 반환하지 않고 생략 수에 기록한다.
검색과 원문 구간 조회는 문서 전체나 색인 전체의 완전성을 보증하지 않는다.

## 게시와 갱신

Go 서버는 SQLite를 읽기 전용으로 열며 문서·키워드 색인·벡터를 변경하지 않는다.
Python indexer가 벡터 쓰기를 마친 뒤 문서 버전과 BM25 색인을 같은 트랜잭션에서 게시한다.
Go 검색은 Qdrant 후보를 게시 장부와 대조하고 리랭킹 후에도 버전을 다시 확인한다.
이전 벡터의 정리가 늦어져도 장부와 다른 버전을 근거로 반환하지 않는다.

FTS5 색인이 없는 장부는 다음 `sync`에서 게시 문서만으로 키워드 색인을 준비한다.
같은 임베딩 설정이라면 벡터를 다시 만들 필요가 없다. Python의 SQLite 빌드에 FTS5 지원은 필요하다.
컨테이너 이미지는 이 기능을 사용하며 테스트도 Python과 Go 양쪽의 실제 SQLite로 확인한다.

장부는 WAL을 사용한다. Go는 읽기 전용 SQL 연결이지만 SQLite의 공유 메모리 파일 접근을 위해
기본 Compose는 `state` 볼륨을 두 서비스에 연결한다. `immutable=1`로 열면 새 WAL 게시를 놓칠 수 있어 사용하지 않는다.
상태 볼륨을 다른 호스트에 복제해 따로 쓰는 분산 구성은 제공하지 않는다.
